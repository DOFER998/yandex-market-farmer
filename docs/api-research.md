# Исследование API Яндекс Маркета

Дата: 2026-10-29. Источник — публичная ветка `main` [xob0t/market-coin-farmer](https://github.com/xob0t/market-coin-farmer).
Это reverse engineering стороннего клиента, **не официальная спецификация и не live-проверка Маркета**.

## Ограничение актуальности

DNS GitHub в терминале недоступен; использован веб-инструмент. Он вернул страницы GitHub с датой обхода «сегодня», но часть raw-файлов — из кеша (до двух месяцев). Например, GitHub показывает 635 строк `yaapi_games.go`, raw — 594. Ключевые игровые вызовы сверены с GitHub-страницей. SHA текущего HEAD получить не удалось. Ссылки ниже привязаны к `main`, следовательно могут сдвигаться. Перед production необходимо клонировать репозиторий, закрепить SHA и повторить сравнение. Утверждения ниже подтверждены прочитанными исходниками, но не гарантированно самым последним коммитом.

Текущий основной вход Python-бота — [QR Passport](bot-auth-research.md), подтверждённый владельцем.
Ниже описан исходный браузерный поток Go-референса, сохранённый как резервный способ.

## Первоначальный вход

[`browserauthservice.go`, Login / waitForLogin / cookiesToNetscape, L59–254](https://github.com/xob0t/market-coin-farmer/blob/main/browserauthservice.go#L59-L254): открывается обычный Chromium с временным профилем; пользователь самостоятельно входит на Passport с retpath Маркета. CDP Storage.GetCookies читает в том числе HttpOnly cookies. Ожидание ограничено пятью минутами, опрос — 1,5 секунды; сигналом служит непустой Session_id. Это ещё не проверка авторизации API. Затем cookies сериализуются в Netscape. Для session cookies референс искусственно задаёт годовой expiry; Python сохраняет исходную session-семантику. Имя может извлекаться из yandex_login. При закрытии окна/таймауте вход прекращается. Python не автоматизирует ввод пароля: `make login` открывает отдельный браузер, ждёт возврата на Маркет и автоматически сохраняет cookies. Ручной Netscape-импорт — резервный вариант.

## Хранение

[`configservice.go`, Account / AddAccountToConfig / SaveGlobalConfig, L26–112](https://github.com/xob0t/market-coin-farmer/blob/main/configservice.go#L26-L112): cookies кодируются base64 и сохраняются в config.yaml вместе с именем и proxy. Base64 не шифрует. SK, версия приложения, glue и время авторизации исключены из постоянной конфигурации. В коде есть логирование аккаунта и запись с os.ModePerm — эту практику не переносим.

В Python: отдельная директория 0700, файл 0600, проверка владельца и symlink, атомарная замена, flock на всю CLI-операцию. В Git и stdout секреты не попадают. Это защита файловыми правами, не шифрование диска. Удалённые/обновлённые сервером cookies сохраняются из jar после запроса, включая ошибочные ответы. Для нескольких копий одного аккаунта в разных файлах блокировка не общая.

## Контекст и транспорт референса

[`yaapi_transport.go`, ensureAuth / getProfileInfo / createAPIRequest / getClient, L20–265](https://github.com/xob0t/market-coin-farmer/blob/main/yaapi_transport.go#L20-L265): GET страницы бонусов извлекает sk, login, -version (desktop), marketFrontGlue, lang. Кеш контекста — час, ключ клиента — proxy+cookies. Jar загружается из base64 Netscape; явного сохранения изменившегося jar обратно в config не найдено. OAuth refresh token не обнаружен.

POST отправляет JSON, Origin/Referer, sk, x-market-app-version, x-market-front-glue, x-market-apphost-target, x-market-page-id=market:fortune-wheel, x-requested-with=XMLHttpRequest, x-retpath-y и browser headers. Target обычно PROMOLOYALTY, bulk — WEB. Timeout 30 секунд. Go использует tls-client/fhttp и Chrome_146, при UA Chrome/151: полного совпадения идентичности нет. Причина выбора fingerprint не доказана A/B-тестом; вероятная мотивация — совместимость с браузерным TLS/HTTP-профилем.

403 обозначается как IP-block, прочие не-200 и пустые ответы — ошибки; автоматического восстановления после 401/403 не найдено. Python не считает любой 403 доказательством блокировки IP: останавливается, как и при CAPTCHA. Контекст обновляется через час/явную auth-check; истёкшая сессия требует повторного входа (QR в боте или локальный браузер). Ошибочные claim-запросы не переотправляются.

## Баланс и ежедневный бонус

[`yaapisservice.go`, константы и GetRewardsJson / ClaimDailyCoins, L15–171](https://github.com/xob0t/market-coin-farmer/blob/main/yaapisservice.go#L15-L171).

База: `https://market.yandex.ru/api/web/market.front.mfPromoLoyalty.MfPromoLoyalty/`.
Оболочка POST: `{"path":"/kolesoprizov?track=menu","params":{}}`.

| Суффикс | Назначение / проверенное поле |
|---|---|
| resolveFortuneWheelMainScreenData | Баланс: result.wheelInfo.userInfo.coins |
| resolveFortuneWheelDailyRewardsScreenData | Доступность: result.dailySignInInfo.rewardAvailable |
| resolveFortuneWheelDailySignInReceiveReward | Claim только при rewardAvailable=true |
| resolveFortuneWheelPrizesScreenData | Просмотр призов; params содержит wheel_ids; в Python не нужен |

Общий путь страницы не означает вращение: чтение баланса и daily независимы от spin. Вращение полностью исключено. Ответ daily claim референс возвращает сырым, тип успешного начисления не описан. Поэтому CLI сообщает submitted_unverified, а не «монеты начислены»; необходимо отдельно сравнить баланс и daily-состояние. Неизвестные/неполные схемы не превращаются в нулевой баланс.

## Игры

[`yaapi_games.go`, структуры L18–75, ClaimGameRewards L94–220, processGamesHubGame / bulk L508–635](https://github.com/xob0t/market-coin-farmer/blob/main/yaapi_games.go#L18-L635).

- AppHost `resolveGamesHubMiniMainScreenDataV2`: gamesSection.games, featuredGame.button.action.openGameAction, missionsSection.missionGroups[].missions. Игры содержат gameId/gameToken; задания — missionId/status/rewardAmount/progress(accumulatedValue,goalValue).
- Legacy POST `/api/resolve/?r=<URL-encoded resolver>`, body `{path,params:[{...}]}`.
- Status resolver: `src/resolvers/gamesHub/resolveGamesHubGameStatusV2:resolveGamesHubGameStatusV2`, params gameToken. Ответ results[0].data.gameStatus.levels: level/requiredScore/rewardPoints/achievedToken/isAchieved.
- Bulk resolver: `src/resolvers/cashbackLevels/fortune/resolveFetchFortuneGameRewardBulk:resolveFortuneGameRewardBulk`, params gameId и levels. Имена уровней получаются удалением RESULT_LEVEL_ и lowercase. Успех: results[0].data.result сопоставляет achievedToken со строкой success.

Референс также отправляет MissionClick, GameEvent(count=недостающий прогресс) и ProcessGameResultV2(score=максимум). Это противоречит задаче: такие операции отсутствуют в Python. Не переносится и слепой bulk market_rush без списка уровней. Python заново читает hub/status, допускает только isAchieved=true плюс непустой achievedToken; неуспешные подтверждения возвращает отдельно. Это консервативное дополнительное условие; семантику повторного claim предстоит проверить аккаунтом. Прогресс задания сам по себе не разрешает начисление.

## Выбор HTTP-библиотеки

| Вариант | Оценка для этого проекта |
|---|---|
| [httpx](https://www.python-httpx.org/advanced/ssl/) | Удобные sync/async API и SSLContext; готового Chrome-профиля в описанном API нет |
| [aiohttp](https://docs.aiohttp.org/en/stable/client_advanced.html) | Асинхронность, jar, SSLContext; потребовалась бы отдельная работа для браузерной идентичности |
| [curl_cffi](https://curl-cffi.readthedocs.io/en/latest/api.html) | Session, CookieJar, browser impersonation, TLS validation; выбран |

Решение: curl_cffi 0.16.3, фиксированный chrome146, соответствующий семейству Go-профиля. UA/client hints задаёт сам профиль, не копируем несогласованный Chrome/151. [Документация профилей](https://curl-cffi.readthedocs.io/en/latest/impersonate/_index.html). Выбор — инженерная гипотеза совместимости, не обещание обхода защиты. Нет ротации IP/профилей, автоматических CAPTCHA-решателей или отключения TLS-проверки. Redirect запрещён: SK не должен уходить на иной origin. Синхронный клиент достаточен для последовательного ядра; будущий aiogram может вызывать его через рабочий поток.

## Нерешённые вопросы / gate перед VPS

1. Закрепить действительный HEAD референса и сверить исходники без кеша.
2. С настоящим аккаунтом проверить HTML-контекст, headers/TLS, срок жизни cookies и Set-Cookie.
3. Сопоставить live-ответы со строгими моделями (особенно optional-поля hub и levels).
4. Проверить daily claim до/после, повторный запуск и смену дня/часового пояса.
5. Для реально сыгранной игры подтвердить meaning isAchieved/achievedToken, повторные награды и частичный bulk. Не создавать прогресс ради теста.
6. Уточнить ошибки sk/session, квоты и Retry-After. Значение 2 секунды между запросами — локальный осторожный default, не известный лимит Яндекса.
7. Ошибка сети после mutation имеет неопределённый результат; нужен durable operation journal перед автономным режимом.

На первоначальном этапе интеграция аккаунтом не проверялась. Все API-ответы автоматических тестов синтетические и не доказывают начисление монет. Результаты последующих реальных запусков пользователя зафиксированы в конце документа.

## Автоматический локальный захват сессии

Команда login использует [Playwright BrowserContext.cookies](https://playwright.dev/python/docs/api/class-browsercontext#browser-context-cookies)
для HttpOnly cookies. Видимый Chrome/Edge либо Chromium открывается с изолированным непостоянным контекстом;
пароль, QR и 2FA вводит пользователь. Ожидается HTTPS-возврат на market.yandex.ru и Session_id,
применимый к странице Маркета; активная страница проверки не принимается. Partitioned cookies не преобразуются в обычные; session expiry сохраняется.
Наличие cookie не объявляется успешной API-авторизацией: для этого есть auth-check.
Браузер закрывается при завершении/ошибке, старый jar заменяется только после успешного захвата.
Реальный вход здесь не выполнен; автоматизация протестирована на подставных ответах браузера.

Детектор challenge не реагирует на строки smartcaptcha в JavaScript/ссылках. Он распознаёт
активные формы checkcaptcha/showcaptcha, challenge URL и известные заголовки страницы проверки.
Неизвестные варианты всё равно отклоняются, если отсутствует валидный HTML/API-контекст.
Список признаков не претендует на полную поддержку всех вариантов антибот-защиты.

Исправление browser gate: Go waitForLogin ждёт Session_id, а getProfileInfo получает SK/glue
отдельным HTTP-запросом. Требовать эти поля в живом DOM браузера было неподтверждённым
отклонением от референса. Оно удалено: браузерный захват и API-проверка снова разделены.

Исправление парсинга версии: appVersionRegex в Go ищет первое значение -version,
соответствующее `.+-desktop\..+`, а не первое произвольное -version. Python-порт
ошибочно проверял только первое поле; теперь выбор соответствует Go. Если контекст всё ещё
не найден, diagnose-auth возвращает только фиксированные флаги/счётчики, без сырых данных.
Никакие значения glue/version по умолчанию не выдумываются.

### Данные реального запуска пользователя

Пользователь выполнил diagnose-auth: sk_present=true, login_present=true, version_matches=1,
desktop_version_matches=0, front_glue_present=true, desktop_marker_mentioned=false.
Следовательно, текущая страница содержит единственное -version без исторического desktop-суффикса.
Теперь это значение передаётся в x-market-app-version без изменения. При наличии desktop-кандидата
сохраняется предпочтение референсного формата, но неоднозначные кандидаты отклоняются.
Пустые значения и управляющие символы запрещены. Это адаптация по фактической диагностике;
приём нового значения впоследствии подтверждён пользователем: balance вернул 7.

## Эфиры: исследование 2026-10-29

### Подтверждено официальной справкой

[Прямые эфиры на Маркете](https://www.yandex.ru/support/market/ru/live-streams):
эфиры доступны в приложении; 15 секунд просмотра дают 1 монету, дневной максимум — 250,
сброс ограничения — в 00:00 по Москве. Монеты используются на странице колеса.
Вращение колеса в нашем проекте по-прежнему исключено.

Расчёт по указанной скорости: 250 × 15 = 3750 секунд = 62 минуты 30 секунд
засчитанного просмотра. Это арифметика, не гарантия начисления при фоновом воспроизведении.

[Правила участия в трансляциях, редакция 14.04.2026](https://yandex.ru/legal/market_live/ru/)
указывают веб-адрес `/live` (п. 1.2), допускают просмотр завершённых эфиров (п. 3.3).
Наличие записей не доказывает начисление монет за них. Раздел 4 описывает отдельные акции
с промокодами; его нельзя использовать как спецификацию API монет за просмотр.

### Что технически ещё не подтверждено

- Работает ли начисление только в native-приложении или также в веб-плеере.
- Засчитываются ли записи, фон, приглушённый звук, несколько эфиров и повторный просмотр.
- Endpoint списка эфиров, остатка дневного лимита, прогресса и получения наград.
- Начисляются ли монеты автоматически во время просмотра или нужен отдельный claim.
- Какие серверные токены, идентификаторы сессии просмотра и подтверждения требуются.
- Совместима ли имеющаяся web-cookie с native API. Наличие рабочей web-сессии этого не доказывает.

Нельзя делать вывод, что 15 секунд соответствуют периоду конкретного heartbeat-запроса:
официальная справка описывает начисление, а не транспортный протокол.
Нельзя отправлять синтетическое время просмотра/события для создания прогресса.
Поддержка эфиров пока не добавлена в клиент; вымышленных resolver-имён нет.

### Полученные и недоступные свидетельства

Публичный `/live` не удалось прочитать: web fetch вернул 400, запрос из терминала — DNSError.
Поиск открытых исходников не дал подтверждённого API вознаграждений эфиров.
Cookies аккаунта не передавались веб-поиску. Перехват трафика приложения не выполнялся.
Запрошена публичная ссылка через «Поделиться» из приложения для проверки конкретного эфира.

Следующий шаг: открыть фактическую ссылку, проверить наличие web-плеера и счётчика.
Если веб-начисление существует, наблюдать обычные запросы при настоящем ручном просмотре,
сопоставив баланс до/после. Секреты и HAR не публиковать. Только после определения роли запросов
решать, есть ли отдельная безопасная операция чтения/получения уже заработанных монет.

### Локальный инспектор для следующего этапа

Добавлена команда `uv run --no-sync python -m scripts.market inspect-live`: отдельный браузер, ручной вход и просмотр,
пассивная запись HTTPS market.yandex.ru/api XHR/fetch в .secrets/live-inspection/run-*/events.jsonl.
Без headers/cookies/строковых значений, с allowlist полей и числовых счётчиков. Это средство
сбора свидетельств, а не реализация API эфиров. Оно не повторяет запросы, не управляет
видеоплеером и не подделывает время просмотра. Отчёт ограничен веб-хостом: отсутствие нужных
запросов в нём не доказывает отсутствие native API. После получения отчёта нужно разобрать
реальные наблюдения до любых новых реализаций начисления.

### Первый фактический браузерный отчёт: run-v0z4hn00

ограничения глубины, массивов и редактирование полей.

Обнаружены реальные POST-методы под

resolveFortuneWheelPrizesScreenData; это не вызовы вращения колеса.

**Ограничение сборщика:** allowlist заменил неизвестные имена на `<field:N>`,
все строки — на `<string>`, часть чисел — на `<number>`. Исходные имена и
значения не сохранены и восстановить их из файла нельзя. Полученного достаточно
для подтверждения существования методов и изменения счётчика, но недостаточно
для точного тела запроса, разбора дневного лимита или реализации API эфиров.
Следующий узкий этап — сбор схемы именно двух обнаруженных методов с сохранением
проверенных имён полей, защитой динамических ключей/секретов, наблюдением счётчика
и общего баланса до/после настоящего просмотра. До выяснения контракта новые
методы в клиент не добавляются и запросы из отчёта не воспроизводятся.

### Формат инспектора v2: полные локальные данные

По запросу пользователя обезличивание отключено: JSON-тела сохраняются целиком,
включая неизвестные ключи, строки, токены, числа и вложенные массивы. Сохраняются

### Полный браузерный отчёт v2: run-9yr22slc

Источник: приватный локальный `.secrets/live-inspection/run-9yr22slc/events.jsonl`.

**Подтверждённый контракт наблюдаемого запроса:**

`POST /api/web/market.front.mfPromoLoyalty.MfPromoLoyalty/resolveLiveStreamUpdateContent`

Тело содержит `path` (путь `/live`, полный query остаётся в приватном отчёте) и
`params.liveHub` с полями:

```json
{
  "balance": 7,
  "max": 250,
  "coinSettings": {
    "amount": 1,
    "periodSeconds": 15,
    "max": 250,
    "enabled": true
  },
  "prepaid": 1

```

Это данные первого ответа, не значения для жёсткого кодирования. `balance`
вырос с 7 (строка 3) до 29 (строка 87). Разность — 22 за примерно 330 секунд

идёт раз в 15 секунд; дополнительные вызовы между ними не увеличили balance.

`params.liveHub.streamId`. Следовательно, это общий метод разных popup:

константой, все popup нельзя трактовать как справку о начислении.

**Вывод о счётчике:** balanceState.balance — отдельный счётчик эфиров,
согласующийся с дневным накоплением; это не текущий расходуемый баланс кошелька.
Последний отдельно подтверждён парными ответами main-screen/balance-request:

из разницы общего баланса нельзя вычислять доход просмотра. Эти вызовы не
реализуются и не воспроизводятся проектом.

**Что теперь подтверждено:** веб-страница возвращает работающий счётчик эфиров
и серверные настройки 1/15 секунд/250; native-приложение не является единственным
местом, где эти данные доступны. Интерфейс указывает полноэкранный просмотр.
Зафиксировано увеличение счётчика при пользовательском сеансе, но инспектор
не фиксировал состояние плеера/видимость вкладки, поэтому запись не проверяет
условия фона, PiP, паузы, отключённого звука или воспроизведения записи.

Отдельного claim эфира среди 54 запросов нет. Нельзя объявлять UpdateContent
безопасным методом только чтения: в его ответах меняется счётчик и он может
участвовать в учёте просмотра. Нельзя считать повтор POST раз в 15 секунд
эквивалентом реального просмотра. До автоматизации остаются невыясненными
источник начального liveHub/sectionHashes, обязательность полей, роль запроса
в начислении, поведение на лимите и при смене дня. Заголовки намеренно не
записаны, поэтому их точный контракт также не подтверждён этим отчётом.

### Мобильный bootstrap подтверждён: run-qfqm9q6b

Мобильный GET /live вернул HTML 1 138 680 байт без десктопной заглушки.
Начальное состояние находится не в window.state и не в script, а в JSON внутри

Точная связка:

### Разобран код клиента: run-jurm2qxm, механизм обновления эфира

Из пользовательского отчёта загружены 7 публичных JS bundle, 1 850 500 байт.
Основная цепочка находится в [browser.LiveStreamPageFuture.cbd5ebb.js](https://yastatic.net/s3/market-b2c-static-production/mf-promoloyalty-touch/browser/browser.LiveStreamPageFuture.cbd5ebb.js),
webpack module 4971. SHA-256 сохранённого UTF-8 исходника:
`f06e779318d89ce8bf62f90b473adf0f55ac9ddf12190f148cf6f45562e1c8c6`.
Ниже смещения символов с нуля в строке source из JSONL, а не смещения JSONL-файла.

Подтверждённая цепочка вызовов:

1. Около 720212: Jt выбирает section.streamInfo; settings находятся в этой секции.
   tn берёт externalStream.verticalId, иначе horizontalId, формирует URL
   `https://frontend.vh.yandex.ru/player/<videoId>`.
2. В 720200–724500: rn связывает startLiveStreamInfoPolling с O и stop с k.
   Компонент an вызывает start в React useEffect при монтировании, stop — в cleanup.
   Этот effect не зависит от isPlaying, onPlay, currentTime или события декодирования.
   В том же компоненте создаётся реальный видеоплеер yt. Независимый effect
   не доказывает, что серверу безразлично наличие воспроизведения.
3. Около 767334: START_LIVE_STREAM_INFO_POLLING читает
   streamInfo.settings.pollingIntervalSeconds; при truthy значении умножает его
   на 1000, иначе использует 10000 мс. В сохранённом мобильном bootstrap настройка
   равна 15, что объясняет период запросов в браузерном отчёте.
4. Источник вызовов объединяет interval и события visibilitychange/focus.
   Дополнительный запрос вызывается при visible + hasFocus, с debounce 300 мс.
   Интервал сам по себе здесь не фильтруется по факту проигрывания видео.
5. uo (около 766300–766640) формирует liveHub из streamId, актуальных
   sectionHashes, исходного liveHubTimeMs, adsSourceScreen и adsPage.
   adsSourceScreen по умолчанию — inactiveTabStream при hidden или отсутствии
   фокуса, иначе stream; adsPage — stream. co добавляет isPipMode=false.
   Для рекламного popup эта же функция получает popup/popup явно.
6. Qa создан через createGrpcClientResolver с методом
   resolveLiveStreamUpdateContent, target PROMOLOYALTY. При streamEnded поток
   прекращается. Иначе обновляются коллекции и секции. После 30 последовательных
   ошибок фронтенд посылает STOP. Это поведение референса, не рекомендация для
   наших повторов операций с неизвестным результатом.
7. Около 748891: Gr объединяет секции по их содержательному типу, сохраняет старые
   sectionHashes, если в обновлении их нет, удаляет deletedSectionIds. Следующий
   запрос берёт хеши из обновлённой коллекции — повторять навечно первый payload
   неверно даже как воспроизведение протокола интерфейса.

Независимый LiveStreamCoinsWidget читает userState.balanceState.balance и
подставляет его в шаблоны отображения. В исследованной цепочке нет отдельного
получения монет (claim). resolveLiveStreamRegisterUserEvent присутствует в таблице
RPC-описаний, но найденные в bundle вхождения — объявление имени и path;
назначение и тело запроса из этого не выводим и не реализуем.

Граница доказательств: JS подтверждает polling интерфейса, но не серверный алгоритм
начисления. Отсутствие проверки isPlaying в одном effect не доказывает отсутствие
серверной проверки плеера, ограничений или иных событий за пределами захваченного
хоста. Отчёт был ограничен market.yandex.ru/api, видеохосты в него не входили.
Значения prepaid и условия начисления без реального просмотра остаются неизвестными.

Решение в рамках исходного ТЗ: не добавлять цикл запросов с изображением активного
просмотра на VPS без плеера. Это нельзя обоснованно назвать получением уже заработанных
наград и оно может искусственно создавать прогресс. Доказан и реализован HTTP
live-status. Для полноценного автосбора эфиров при сохранении запрета на искусственный
прогресс необходимо подтверждённое реальное воспроизведение либо отдельный контракт
получения ранее заработанной награды; такого контракта в материалах не найдено.

## Подтверждённое время следующей ежедневной награды

В локальном отчёте `.secrets/live-inspection/run-9yr22slc/events.jsonl` сопоставлены request/response
для `resolveFortuneWheelDailyRewardsScreenData`. Путь ответа:
`result.dailySignInInfo.nextRewardTs`. Зафиксировано `rewardAvailable=false`,
`nextRewardTs=1793307600` (Unix **секунды**, не миллисекунды). Соседние ключи: plan, subscription.
Исходный отчёт приватный, в репозиторий не включается; тест содержит только эти несекретные поля.

Python daily_status читает bool доступности и UTC timestamp. Отсутствие/ноль таймера означает
неизвестное время, неверные типы/диапазоны дают ProtocolError. Не предполагается локальная полночь.
После отправки daily claim worker отдельно перечитывает состояние: если чтение не удалось или
rewardAvailable остаётся true, результат считается неопределённым и автосбор останавливается.
Недоступность бонуса после запроса не доказывает сумму начисления; исход по-прежнему partial.

APScheduler ставит date-задачу на серверное время + случайные 30–90 секунд, сохраняемые в БД.
Задержка распределяет обращения; гарантий маскировки автоматизации нет. Нет таймера — отдельная
проверка не ранее 6 часов. Игровые награды не имеют подтверждённого такого же reset timestamp:
их доступность проверяется отдельной ручной операцией, независимо от daily.

### Исправление GamesHub: завершённая миссия без progress (29.10.2026)

В двух сохранённых ответах `resolveGamesHubMiniMainScreenDataV2` из локального
`run-9yr22slc` обнаружены 11 игр и 3 миссии. У миссии со статусом
`MISSION_STATUS_COMPLETED` полностью отсутствует `progress`, у двух DEFAULT-миссий
прогресс присутствует. Предыдущий Python-парсер требовал progress у каждой миссии,
поэтому оба ответа воспроизводимо давали ProtocolError на этом поле.
Go использует struct с нулевыми значениями при отсутствии полей
([определение ответа](https://github.com/xob0t/market-coin-farmer/blob/main/yaapi_games.go#L22-L51)).
Python теперь хранит отсутствующий прогресс как None; это не доказательство права
на начисление. Если progress присутствует, тип и оба счётчика по-прежнему проверяются.
После исправления оба сохранённых ответа разобраны офлайн. Это подтверждает ошибку
парсера, но не доказывает, что ответ конкретного сбойного запуска был идентичен.

`make diagnose-games ACCOUNT=main` читает hub и статусы всех игр без начислений.
Ответы непрерывно сохраняются в `.secrets/games-diagnostics/run-*/events.jsonl`
с правами 0600 в каталоге 0700. Файл содержит оригинальные ответы и может включать
игровые токены; его нельзя коммитить или отправлять в Telegram. CAPTCHA, истечение
авторизации и rate limit останавливают чтение. Ошибка схемы отдельной игры записывается,
после чего проверяются остальные. Реальная выдача заработанной награды ещё требует
интеграционной проверки; mock-тесты этого не подтверждают.
