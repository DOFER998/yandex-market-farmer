## Обновление авторизации

Фактическая последовательность:

```text
GET market.yandex.ru/kolesoprizov
302 → passport.yandex.ru/auth/update?retpath=…
302 + Set-Cookie → market.yandex.ru/kolesoprizov
200 → sk, login, version, marketFrontGlue
```

Обновились `Session_id`, `sessar`, `sessionid2`, `yandex_login`, `sessguard`,
`mda2_beacon`, `lah`. До обновления даты окончания основных cookies ещё не наступили.
Причиной ошибки был отказ клиента следовать любому 3xx, а не доказанное истечение cookies.

Теперь клиент разрешает ограниченную цепочку GET только между указанными HTTPS host/path,
сохраняет jar атомарно под блокировкой. POST начисления не переотправляется. Проверены
враждебные redirects, CAPTCHA, циклы, порты, HTTP и сохранение обновлённой cookie.
OAuth refresh token в этой цепочке отсутствует. Если Passport действительно требует нового
входа, автоматическое обновление не поможет — нужен QR, без удаления существующего аккаунта.

Живой read-only запуск после обновления: `a78889ce-22e8-45bf-81cd-385f2e29aa20`,
авторизация восстановлена, баланс прочитан. Выключенный автосбор сам не включался.

## Эфиры без браузера

Мобильный `/live` предоставляет `streamId`, `liveHubTimeMs`, `sections`,
`userState.balanceState`. Для HTTP используется мобильный профиль `chrome131_android`.

`POST /api/web/market.front.mfPromoLoyalty.MfPromoLoyalty/resolveLiveStreamUpdateContent`:

```json
{
  "path": "/live",
  "params": {
    "liveHub": {
      "streamId": "из bootstrap",
      "sectionHashes": [],
      "liveHubTimeMs": 0,
      "adsSourceScreen": "stream",
      "adsPage": "stream",
      "isPipMode": false
    }
  }
}
```

Это описание формы, не готовое тело для отправки: timestamp и sectionHashes берутся из
bootstrap, timestamp остаётся неизменным при последовательных опросах. Частичные sections
сливаются с сохранёнными, удалённые sectionId исключаются. Заголовки включают sk,
версию, frontGlue, AppHost target PROMOLOYALTY, origin/referer.

После подтверждения пользователем закрытия эфира изолированный HTTP-прогон дал:
счётчик 241→245, кошелёк 547→551 (`live-isolated.jsonl`). Повторная проверка уже
`LiveClient` дала 246→249 и 572→575. Видео не запускалось и не декодировалось.
Отдельного claim в проверенной цепочке нет: начисление связано с UpdateContent.

Клиент использует интервал из stream settings, не меньше периода coinSettings; останавливается
при streamEnded, enabled=false или достижении меньшего из двух сообщённых max.
Лимит 250 и период 15 секунд были получены от сервера, а не зашиты как условия начисления.
Время ежедневного сброса не подтверждено: после лимита используется часовое чтение bootstrap.
Завершение эфира обрабатывается отдельно: текущий `/live` перечитывается сразу и затем раз в минуту,
пока не появится другой streamId. Это поведение проверено контрактными тестами; реальное завершение
и смена стрима во время данного исследования ещё не наблюдались.
Эта автоматизация экспериментальна; отказ API не блокирует daily и не подтверждает начисление.

## Исполнение и Telegram

- Daily остаётся в APScheduler с deadline из БД. Игры и эфиры имеют независимые фоновые задачи.
- Каждый сетевой участок использует общий account lock; ожидание периода не держит блокировку.
- Дополнительные задачи выключены по умолчанию и требуют включённого автосбора аккаунта.
- GetUpdates соблюдает retry_after, восстанавливается после 5xx/timeout с ограниченным backoff.
- Отправка сообщения после timeout не повторяется автоматически: исход доставки неизвестен.
- Просроченный callback ack не прерывает переход по меню. QR-экран восстанавливается после
  отсутствующего или неподходящего сообщения. Полный повторный QR-вход через UI после этих
  изменений ещё требует пользовательской проверки; начало новой QR-сессии проверено живым API.
- Логи содержат стадию, тип ошибки, разрешённую причину и место в коде, без токенов и cookies.

Unit-тесты проверяют контракты и восстановление, но не заменяют перечисленные живые прогоны.
Длительный автономный запуск на VPS после этих изменений ещё не проверен.
