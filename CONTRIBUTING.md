# Разработка

Проект создаётся с активным использованием ИИ — вайбкодинг здесь не скрывается.
AI-generated изменения проходят те же проверки, что и ручные. Автор PR отвечает за понимание
изменений; зелёные mock-тесты не являются доказательством работы внешнего API.

## Подготовка

```bash
make sync
make check
```

Для работы с реальной БД и ботом: `make setup-env db-up start`.
Интерпретатор Python 3.13, зависимости — только через uv. Команды проекта доступны через `make help`.
Настройки и секреты — в `.env`, не в исходниках. Форматирование — Ruff, строковые литералы с одинарными кавычками.

## Работа с изменениями

1. Создайте `feature/*`, `fix/*` или `docs/*` от актуальной `dev`.
2. Внесите минимально необходимое изменение, добавьте тесты поведения, обновите документацию.
3. Выполните `make check`; при изменении persistence — также `make test-postgres`.
4. Откройте PR в `dev`. Укажите результат, проверку и ограничения; не прикладывайте секреты и raw-отчёты.
5. Стабильные изменения попадают в `main` через release PR. [Порядок выпуска](docs/releases.md).

## Границы архитектуры

- `src/market` не зависит от Telegram, PostgreSQL и планировщика.
- `src/services` получает зависимости через конструкторы; SQL остаётся в репозиториях.
- Роутеры aiogram вызывают сервисы, представления формируют текст, клавиатуры — кнопки.
- HTTP выполняется вне event loop. Нельзя отменять ожидание worker и освобождать account lock,
  пока запрос, способный изменить состояние, ещё выполняется.
- Неизвестный результат начисления не повторяется автоматически.
- Новый API-контракт подтверждается исходниками или приватным отчётом; догадки отмечаются явно.

Рулетка, покупки, расход монет, фальсификация прогресса и обход CAPTCHA не входят в проект.
Не добавляйте их под видом тестирования или «оптимизации» транспорта.

## Зависимости и миграции

Добавляйте только необходимые зависимости: `uv add`, серверные — `uv add --optional server`.
Коммитьте `pyproject.toml` вместе с `uv.lock`. Обновления библиотек — отдельный обозримый PR.
Alembic-миграции проверяются upgrade → downgrade → upgrade на временной PostgreSQL-схеме.
Не редактируйте опубликованные миграции: добавляйте следующую.
